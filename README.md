# GitMind frontend

React, TypeScript, Vite, Tailwind CSS, React Router. Интерфейс использует настоящий HTTP API; демонстрационных данных и имитации запросов в приложении нет.

## Запуск

Используйте Node.js 24 и установите зависимости через `npm ci`.

1. Скопируйте `.env.example` в `.env.local`.
2. Задайте `VITE_API_BASE_URL` — базовый URL API без пути эндпоинта. Пустая строка означает тот же origin, что у frontend.
3. Выполните `npm run dev`.

Для backend из [README ветки dev](https://github.com/pp-sem7-team/backend/blob/dev/README.md), запущенного локально на указанном там адресе:

```dotenv
VITE_API_BASE_URL=/api
VITE_API_PROXY_TARGET=http://localhost:8080
```

`VITE_API_PROXY_TARGET` включает только dev proxy Vite: `/api/*` перенаправляется на заданный сервер с удалением префикса `/api`. Обязательного адреса backend в коде нет. После изменения окружения перезапустите Vite. Все переменные `VITE_*` являются публичной конфигурацией; секреты в них помещать нельзя.

В production настройте reverse proxy к API на том же origin либо укажите полный API URL и разрешите frontend origin в CORS на backend. Dev proxy не входит в production-сборку. Хостинг должен возвращать `index.html` для frontend-маршрутов, включая `/workspaces/:workspaceId` и `/branches/:branchId`, а API-маршруты передавать backend.

## Подключённые сценарии

- Регистрация и вход: `POST /auth/register`, `POST /auth/login`, затем `GET /users/me`.
- Обновление и выход: `POST /auth/refresh`, `POST /auth/logout`.
- Рабочие области: `GET/POST /workspaces`, `GET /workspaces/{workspace_id}`.
- Ветки: `GET/POST /workspaces/{workspace_id}/branches`, `GET /branches/{branch_id}`.
- Изменения: `POST/GET /branches/{branch_id}/changes`, `GET /changes/{change_id}`.

Списки используют `items`, `limit`, `offset`, `total`; страницы запрашивают по 10 элементов и предлагают переходы «Назад»/«Далее». Сайдбар показывает ресурсы текущей страницы, полный список доступен через «Рабочие области».

Закрытая ветка запрещает ввод и отправку diff. Ошибки не стирают введённый текст. HTTP 202 означает принятие изменения: отображается `pending`, а состояние анализа видимых изменений и выбранного Change опрашивается каждые 2,5 секунды без параллельных циклов. Опрос отменяется при смене страницы/ветки и прекращается при `done`/`failed`. При сетевой ошибке опрос приостанавливается до нажатия «Повторить». После перезагрузки pending-изменения снова загружаются из истории. Статус анализа и данные результата показываются только из ответа сервера.

Компоненты коммитов и PR сохранены; их редактирование и генерация относятся к Issue #5 и здесь не подключены.

## Сессия

Пара токенов хранится в памяти и в `sessionStorage` на время вкладки, чтобы переживать перезагрузку. Пароли не сохраняются. При недоступном storage сессия работает только в памяти. Такое хранение доступно JavaScript и **не защищает токены от XSS**; текущий контракт не предоставляет HttpOnly cookie. Сессии вкладок независимы; копирование вкладки браузером может копировать её sessionStorage, поэтому следует входить отдельно в новой вкладке, а не переносить токены вручную.

До завершения `GET /users/me` защищённый контент скрыт. При 401 клиент выполняет один общий refresh для ожидающих запросов, заменяет всю пару токенов и повторяет запрос один раз. Запоздалый 401 использует уже обновлённую пару. Неудачный refresh или повторный 401 очищает сессию и возвращает пользователя ко входу. Запросы старой сессии не повторяются от имени нового аккаунта.

Logout дожидается текущей ротации, очищает локальную сессию и отправляет актуальный refresh token для отзыва. Если сервер не подтвердил отзыв, на странице входа отображается сообщение об этом; локальный выход всё равно выполнен.

## Проверки

```sh
npm run build
npm run lint
npm test
```

Build включает проверку TypeScript со `strict: true`. `npm test` также проверяет типы тестов и запускает встроенный Node test runner: HTTP-клиент, refresh/logout, ошибки, отмена, передача diff, 202 и серверный рендер компонентов состояний анализа. Изолированные ответы транспорта существуют только в тестах и не включаются в приложение. Новые зависимости не добавлены.

### Проверка реального backend

При реализации Issue #3 адрес `http://localhost:8080/health` из backend README не отвечал (connection refused). `.env.local` и иной настроенный адрес API в frontend отсутствовали. Инфраструктура не запускалась и не изменялась. Автотесты не подтверждают интеграцию с настоящим сервером и не заменяют проверку в браузере.

После запуска настоящего backend необходимо проверить:

1. Регистрацию, несовпадение паролей, дубликат email, вход с неверным паролем.
2. Обновление защищённой страницы, истёкший access token, отозванный refresh token, выход с отзывом токена.
3. Создание и просмотр рабочих областей и веток, дубликаты имён, пустые списки и более 10 ресурсов.
4. Прямые ссылки на существующие и отсутствующие workspace/branch.
5. Реальный diff: 202 → pending → done/failed, сохранение текста при ошибках 400/409/413/503, истечение сессии при отправке, закрытую ветку.

### Расхождения backend и контракта

Основной источник: [HTTP_API.md](https://github.com/pp-sem7-team/docs/blob/main/HTTP_API.md). Также изучены [Issue #3](https://github.com/pp-sem7-team/frontend/issues/3), [PR #4](https://github.com/pp-sem7-team/frontend/pull/4), [GitFlow](https://github.com/pp-sem7-team/docs/blob/main/GITFLOW.md) и конфигурация backend `dev` (commit `53f74ab`).

В [internal/changes/dto.go](https://github.com/pp-sem7-team/backend/blob/53f74ab062cfefd47b947ad01f1b5330a4e0a825/internal/changes/dto.go) поле `commit` возвращается как `null`, хотя контракт описывает объект Commit. Контрактный тип Change сохранён; история защищена от null при отображении и не подставляет фиктивный коммит. В router backend также пока нет эндпоинтов генерации/редактирования Commit и PR — они не используются этой задачей. CORS middleware в изученном router отсутствует; для локального подключения предусмотрен настраиваемый proxy.
